# ПОС — преподавательская оценка студентов


## Сборка и запуск

Нужен установленный **JDK 25**. В проекте есть Gradle Wrapper **9.4.0**:
отдельно устанавливать Gradle не нужно. Java 25 выбрана из уже установленных
JDK окружения разработки. Preview-возможности не используются.

```bash
./gradlew clean build
./gradlew --console=plain run
```

При нескольких JDK укажите подходящий `JAVA_HOME`. На macOS:

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 25)
./gradlew clean build
```

Первый запуск скачивает зависимости из Maven Central и дистрибутив Gradle.
`run` перед запуском приложения проверяет стиль production-кода и тестов,
но не запускает тесты и JaCoCo. Для полной проверки используется `build`.

В IntelliJ IDEA откройте корень проекта и подключите `build.gradle`:
правой кнопкой → **Import Gradle Project**. Для запуска с гарантированной
проверкой стиля используйте задачу **Gradle → application → run**.
Прямой запуск `Main` кнопкой IDE обходит Gradle-проверки.

## Команды

Команды вводятся по одной на строку. В именах допустимы пробелы;
дробные числа можно записывать через точку или запятую.

| Команда | Действие |
| --- | --- |
| `student add Анна Иванова` | Добавить студента; вывести его ID |
| `student list` | Список студентов |
| `criterion add Домашняя работа \| 10 \| 40` | Добавить название, максимум и вес |
| `criterion list` | Текущий рубрикатор с ID, максимумами и весами |
| `grade set 1 1 8` | Впервые поставить студенту 1 по критерию 1 балл 8 |
| `grade list 1` | Посмотреть оценки студента 1 |
| `grade correct 1 1 9` | Исправить существующую оценку |
| `grade cancel 1 1` | Отменить существующую оценку |
| `total 1 strict` | Итог студента 1 только при наличии всех оценок |
| `total 1 zero` | Итог студента 1 с нулями вместо пропусков |
| `report strict` | Ведомость и среднее среди рассчитанных итогов |
| `report zero` | Ведомость с выбранной политикой пропусков |
| `export strict exports/result.csv` | Экспортировать свежую ведомость |
| `help` / `exit` | Помощь / завершение работы |

Для `total` и `report` политика необязательна: по умолчанию `strict`.
В команде экспорта политика обязательна, остаток строки — путь,
в том числе с пробелами. Экспорт создаёт родительские каталоги и
**перезаписывает** указанный файл.

Ведомость хранится в памяти **до завершения процесса**. Постоянное хранение
и повторный импорт CSV не реализованы: в функциональных требованиях PDF
они не заданы. CSV предназначен для выгрузки итогов, а не восстановления
агрегата. Дата и комментарий оценки также необязательны и опущены.
Изменение/удаление студентов и критериев в PDF названы необязательными;
исправление и отмена оценок реализованы полностью.

## Сквозная демонстрация

```bash
./gradlew --console=plain run < examples/demo.txt
```

Сценарий создаёт двух студентов и два критерия, выставляет оценки,
показывает оценки и итог, проверяет ошибки неизвестного критерия и
превышения максимума, исправляет и отменяет оценку, демонстрирует обе
политики пропусков и создаёт `exports/strict.csv` и `exports/zero.csv`.
Ошибки двух команд в сценарии ожидаемы: сессия продолжает работать.

Контрольные результаты Анны:

- `8/10` с весом `40` и `15/20` с весом `60` → **7.70**;
- отклонённое исправление на `12/10` оставляет итог **7.70**;
- исправление первой оценки на `10/10` → **8.50**;
- отмена экзамена → итог не определён в `strict`, **4.00** в `zero`;
- восстановление экзамена → **8.50** в консоли и CSV.

У Бориса есть только `10/10` за домашнюю работу: строгий итог отсутствует,
итог с нулём за экзамен — **4.00**. Поэтому среднее в итоговой ведомости
составляет **8.50** для `strict` и **6.25** для `zero`.

## Зафиксированные бизнес-решения

PDF не задаёт точную шкалу итогов, правила пропусков и округления.
В реализации приняты следующие явные решения:

1. Итог находится на шкале от 0 до 10.
2. Максимум и вес каждого критерия строго положительны. Балл может быть
   дробным и должен лежать в `[0, максимум]`.
3. Веса относительные: `40/60`, `4/6` и `0.4/0.6` дают одинаковый результат.
4. Формула: `10 × Σ(вес × балл / максимум) / Σ(вес)`.
5. В `strict` пропуск означает отсутствие определённого итога.
   В `zero` пропуск даёт нулевой вклад, но его вес остаётся в знаменателе.
   Отсутствующая оценка и явно выставленный ноль различаются.
6. Числа представлены `BigDecimal`. Промежуточные деления используют
   `DECIMAL128`, итог округляется до двух знаков `HALF_UP`.
7. Пустой рубрикатор не позволяет рассчитать итог студента.
   Пустой список студентов отображается и экспортируется как пустая сводка.
8. Для пары «студент + критерий» допускается одна активная оценка.
   Повторное выставление отклоняется; замена выполняется через `correct`.
9. Неудачное добавление/исправление не меняет данные или счётчики ID.
10. Итоги не хранятся отдельными изменяемыми полями и не кэшируются.
    Расчёт всегда использует текущие оценки и текущий рубрикатор.
11. Сводка показывает число студентов, число рассчитанных итогов и среднее
    **отображаемых итогов**. Отсутствующие итоги в среднее не входят.
12. Критерии после создания неизменяемы. Добавление нового критерия сразу
    влияет на полноту оценивания и последующие расчёты.

## Карта DDD

Общий язык используется одинаково в требованиях, коде и интерфейсе:

| Термин | Тип | Ответственность |
| --- | --- | --- |
| Студент | `Student`, Entity | Стабильный ID и непустое имя |
| Критерий | `Criterion`, Entity | ID, название, положительные максимум и вес |
| Оценка | `Evaluation`, Entity | Факт оценки с идентичностью пары ID студента и критерия |
| Балл | `Score`, Value Object | Неизменяемое значение вместе с верхней границей |
| Ведомость | `Gradebook`, Aggregate Root | Студенты, рубрикатор, оценки и допустимые изменения |
| Итог | `FinalScoreCalculator`, Domain Service | Согласованный взвешенный расчёт |
| Хранилище ведомости | `GradebookRepository`, Repository port | Контракт загрузки/сохранения агрегата |

Entity сравниваются по идентичности: исправленная оценка остаётся той же
оценкой студента по критерию, даже когда балл изменился. Имена студентов
не являются идентификаторами, однофамильцы допустимы.
VO сравнивается по содержимому: `Score(8.0, 10)` равен `Score(8.00, 10.0)`;
десятичный масштаб нормализуется. У балла нет отдельного ID и сеттеров.

Один агрегат выбран осознанно: приложение обслуживает один курс,
однопоточный консольный процесс и небольшой объём данных. Студенты,
рубрикатор и оценки образуют одну границу согласованности. Собственного
репозитория для каждого внутреннего объекта не требуется.

Изменения проходят через `Gradebook`. Он проверяет существование студента
и критерия, запрещает дубликаты оценок и возвращает неизменяемые снимки
коллекций. Фабрика берёт диапазон у найденного критерия, а `Score`
проверяет границы. Произвольный внешний `Evaluation` нельзя вставить в
агрегат: такого публичного метода нет. Поэтому обход консоли не обходит
доменные ограничения. Модель содержит поведение и инварианты.

Расчёт вынесен в Domain Service, поскольку правило использует весь
рубрикатор и набор оценок. Это не операция одной оценки или студента.

## Архитектура и структура пакетов

Выбрана облегчённая **Ports & Adapters**. Один Gradle-модуль;
группировка начинается с предметной области `studying.pos`, затем
идёт слой и конкретная роль. Точка входа — `studying.Main`.

```text
src/main/java/studying/
├── Main.java
└── pos/
    ├── domain/
    │   ├── model/          Student, Criterion, Score, Evaluation, Gradebook
    │   ├── exception/      DomainException
    │   ├── factory/        EvaluationFactory
    │   ├── repository/     GradebookRepository
    │   ├── services/       FinalScoreCalculator
    │   └── strategy/       MissingGradePolicy + impl/
    ├── application/
    │   ├── model/          StudentResult, ResultReport
    │   ├── services/       PosFacade
    │   └── port/           ResultExporter
    ├── infrastructure/
    │   ├── console/        ConsoleApplication
    │   ├── repository/     InMemoryGradebookRepository
    │   └── export/         CsvResultExporter
    └── config/             PosModule — composition root
```

Зависимости исходного кода направлены внутрь:

```text
ConsoleApplication ──→ Application ──→ Domain
InMemoryGradebookRepository ──→ Domain / GradebookRepository
CsvResultExporter ──→ Application / ResultExporter
Main / PosModule ──→ контейнер и выбранные реализации
```

## Применённые паттерны

Ровно по одному из каждой требуемой группы:

| Группа | Паттерн и место | Решаемая проблема |
| --- | --- | --- |
| Порождающие | Фабрика: `EvaluationFactory` | Единый путь создания оценки с диапазоном реального критерия |
| Структурные | Facade: `PosFacade` | Координация загрузки, доменных операций, сохранения и экспорта вне UI |
| Поведенческие | Strategy: `MissingGradePolicy` | Два реально выбираемых правила обработки пропусков |

Фабрика — доменная фабрика из примера задания; она не выдаётся за
классический GoF Factory Method с наследованием создателей.
Принадлежность критерия рубрикатору контролирует агрегат до вызова фабрики.
Facade непосредственно реализует небольшие use cases; дополнительные
пустые сервисы-посредники не вводятся. Стратегии меняют только правило
пропуска, а общая формула остаётся одной в Domain Service.

## Тесты, покрытие и стиль

```bash
./gradlew test
./gradlew integrationTest
./gradlew jacocoTestCoverageVerification
./gradlew checkstyleMain checkstyleTest
./gradlew clean build
./gradlew run --dry-run
```

JUnit Jupiter 6.0.3 проверяет инварианты, граничные и ошибочные ситуации,
исправление/отмену, расчёты с разными весами и максимумами, пропуски,
устойчивость снимков, разбор команд, восстановление после ошибок и CSV.
Обычные тесты повторяют предметные пакеты в `src/test/java/studying/pos`.
Общие тестовые подстановки находятся в `support`.

Интеграционные проверки находятся в `integration`, помечены
`@Tag("integration")`, запускаются отдельной задачей и входят в `check`.
Они проверяют настоящий DI-граф, порт экспорта и точку входа.
Их выполнение отключено в JaCoCo и не добавляет проценты юнит-покрытия.

Юнит-тесты сценариев и консоли используют подставные исходящие порты,
а CSV-адаптер проверяется отдельно с изолированным `@TempDir`.
Тесты не требуют сети, сервера, БД, задержек или конкретного порядка.

Блокировки проверены в изолированных временных копиях: импорт со звёздочкой
даёт ошибку Checkstyle и не допускает `run`; временный минимум покрытия 100%
даёт ошибку verification, сохраняя HTML-отчёт. В рабочем проекте остались
исправный код и согласованный минимум 80%.

Отчёты после проверки:

- юнит-тесты: `build/reports/tests/test/index.html`;
- интеграционные: `build/reports/tests/integrationTest/index.html`;
- покрытие: `build/reports/jacoco/test/html/index.html`;
- точные счётчики: `build/reports/jacoco/test/jacocoTestReport.xml`;
- стиль: `build/reports/checkstyle/main.html` и `test.html`.
